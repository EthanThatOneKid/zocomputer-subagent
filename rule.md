# Zo subagent delegation rule

CONDITION: A task contains at least five independent subtasks, or explicitly asks for parallel subagents, fan-out, or a swarm.

INSTRUCTION: Use the zocomputer-subagent workflow when a task contains at least five independent subtasks or explicitly asks for parallel subagents, fan-out, or a swarm. Keep the active parent conversation on a capable model for decomposition, supervision, synthesis, and verification; the skill cannot change the parent's model. Choose each child's model independently from the caller's current `/models/available` catalog: use a fast model for narrow, mechanical, easily checked work and a capable model for ambiguous, multi-step, design, code-review, or high-consequence work. Use `model_name="auto"` only when automatic routing is preferable; it is not a cost cap. Put per-child model IDs in JSONL task objects via `scripts/spawn.ts`; use its `--model` value only as the fallback. Give each child one narrowly scoped, self-contained task, complete context, and an explicit output format; tell each child not to spawn more agents. Limit delegation to five concurrent children and twenty total children; default to two concurrent requests and one attempt per child. Do not blindly retry or resume timed-out/cancelled children because the remote request may still be running and a retry may duplicate credit use. The runner itself does not recurse, but the no-delegation instruction is not a hard tool restriction; supervise children and keep batches small. Collect all child results before synthesizing and verifying them in the parent conversation. Do not delegate secrets, irreversible actions, or final external communications. Prefer the session-provided `ZO_CLIENT_IDENTITY_TOKEN` and fall back to a dedicated `ZO_SUBAGENT_API_KEY` only when configured.
